# 有两种输入模式，而且 OGCRL 里就是靠配置切换的。

在 robot_gc.yaml 里有一个 observation 参数，注释已经写了可选值是 state、visual，代码里训练时会把它传给 robot_gc_dataset.py。这里的逻辑很直接：如果是 visual，就把 head_camera 图像转成 64×64 的图像观测；如果是 state，就直接用 state 向量作为观测。

所以你可以理解为：

visual 模式：输入图像观测，适合视觉策略。
state 模式：直接输入状态序列，适合状态策略。
不过要注意一点，当前这份代码里真正实现的分支只有 visual 和 state 两种，没有看到一个完整实现的 both 分支；虽然配置注释里写了 both，但实际转换函数只处理了这两种。训练入口在 robotworkspace.py 会把这个参数原样传进去，所以实际跑哪个模式，完全取决于命令行里怎么覆盖 observation。

# 目标
同一个目标在两种模态下的表示”。

在训练里，OGCRL 的 goal 是跟输入模态绑定的：如果你设的是 visual，batch['actor_goals'] 和 batch['value_goals'] 就来自图像观测；如果你设的是 state，它们就来自状态向量。这个逻辑在 robot_gc_dataset.py 里体现得很直接，goal 是从 observations 里采样出来的。

但在评估和保存 goal 的时候，代码会把两种信息都存进同一个 goal 文件里，也就是同时保存 state 和 head_camera。然后在 eval_multi_dp.py 里根据 args.observation 选择用状态 goal 还是图像 goal。

所以结论是：

训练时：goal 也分 visual / state，两者和 observation 模式一致。
保存时：同一个目标文件里通常同时包含 state 和 head_camera。
语义上：不是两种不同目标，而是同一目标的两种表示方式。

## 目标获取逻辑

这里的“目标”并不是两套完全不同的目标，而是同一个目标在两种观测表示下的两种形式：state 形式和 visual 形式。代码里是按当前训练/评估所选的 observation 模式来决定使用哪一种表示。

### 训练时

训练时的目标来源不是手工指定的一个固定目标，而是从数据集中的观测序列里采样出来的。核心逻辑在两个地方：

1. 在 robotworkspace.py 里，训练入口会把 cfg.observation 传给 convert_replaybuffer_to_rl_dataset(..., observation_type=cfg.observation)。
2. 在 robot_gc_dataset.py 里，数据集会根据 observation_type 生成不同形式的 observations。

#### state 模式
- 进入 `observation_type == "state"` 分支后，训练数据集里的 `observations` 直接使用 `data["state"]`。
- 后面 `GCDataset.sample()` 会从这些 observations 中采样 `value_goals` 和 `actor_goals`。
- 也就是说，训练时的 goal 本质上就是“某个状态向量”，例如未来某一步的状态。
- 这时网络的输入和 goal 都是状态形式，因此适合状态策略。

#### visual 模式
- 进入 `observation_type == "visual"` 分支后，训练数据集里的 `observations` 使用的是 `head_camera` 图像先转成 `(240, 320, 3)`，再 resize 到 `(64, 64)` 的图像。
- `GCDataset.sample()` 仍然是从这些 observations 中采样 `value_goals` 和 `actor_goals`，只是此时采样出来的目标已经是图像形式了。
- 也就是说，训练时的 goal 本质上就是“某个图像目标”，例如未来某一步的相机观测。
- 这时网络的输入和 goal 都是视觉形式，因此适合视觉策略。

#### 训练时的统一理解
- 无论是 state 还是 visual，训练阶段的目标本质上都是“从当前轨迹中采样出来的某个未来状态/观测”。
- 区别只在于：
  - state 模式下，goal 是状态向量；
  - visual 模式下，goal 是图像观测。

### 保存目标时

在 `convert_replaybuffer_to_rl_dataset()` 的开头，如果 `save_goal_path` 不为空，就会把第一条轨迹的起点到终点之间均匀选取 5 个时刻，提取出对应的目标数据并保存成一个 pickle。

保存内容包含两种表示：
- `state`: 状态向量
- `head_camera`: 图像观测

也就是说，保存时并不会只存一种“目标”，而是把“同一个目标”同时保存成两种表示，方便后续不同模态的评估复用。

### 评估时

评估逻辑在 eval_multi_dp.py 里，读取这个 goal 文件后，再根据当前的 `args.observation` 选择使用哪一种表示。

#### state 模式
- 如果 `args.observation == "state"`，则初始化 agent 时使用 `example_goals[...][agent_id]["state"]` 作为 goal。
- 推理时也会把当前观测传给策略网络的 `observations`，并且把 goal 传成状态向量：
  - `actor_fns[id](observations=observations[id]["agent_pos"], goals=example_goals[goal_index][id]["state"], ...)`
- 这表示评估时也会用 state 目标来驱动策略。

#### visual 模式
- 如果 `args.observation == "visual"`，则评估时使用 `example_goals[...][agent_id]["head_camera"]` 作为 goal。
- 推理时对应地把当前视觉输入和视觉目标传给策略网络：
  - `actor_fns[id](observations=observations[id]["head_cam"], goals=example_goals[goal_index][id]["head_camera"], ...)`
- 这表示评估时也会用视觉目标来驱动策略。

#### 评估时的统一理解
- 评估时并不是“重新生成一个新目标”，而是从保存好的 goal 文件中读取目标，然后根据当前模态选择对应的表示来执行。
- 所以：
  - state 模式下，评估使用 state goal；
  - visual 模式下，评估使用 image goal。

### 最终结论
- 训练时：goal 也是跟 observation 模式绑定的，state 模式下是 state goal，visual 模式下是 visual goal。
- 保存时：同一个目标文件里通常同时保存 state 和 head_camera 两种表示。
- 评估时：从这个文件中按当前 observation 模式读取相应的 goal 表示。
- 所以，严格来说不是“两个不同目标”，而是“同一个目标的两种表示形式”。

# 评测时观测获取罗技

state 和 visual 两种模式。

实际代码里，评测时的“观测”并不是每帧都重新组一遍给策略用，而是先 env.reset() 得到一次 raw_obs然后在循环外只构造一次 observations
循环中每一帧，策略输入还是这份初始观测两种模式分别是：

state 模式：用 raw_obs['agent'][...]['qpos'] 取初始关节状态，再拼上夹爪状态，作为 observations[id]["agent_pos"]
visual 模式：用 get_model_input(raw_obs, ...) 从 raw_obs['sensor_data'][camera]['rgb'] 取头相机图像，resize 到 64×64，作为 observations[id]["head_cam"]
补一句关键点：循环里每帧会调用 raw_obs = env.get_obs()，但这主要是给后面的轨迹规划取当前关节状态用的，不是重新喂给 actor 的观测。也就是说，策略观测在这份代码里是“reset 时取一次”，不是“每帧更新”。
